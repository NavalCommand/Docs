# Repeatable movement and first facility launch implementation

Implemented against current checkouts after Tasks 007, 009, 010 and 011. Domain ownership, canonical schema, RPCs, native ABI, independent runtime/harness, shared build infrastructure and managed output rules are preserved. Tasks 008 and broader formation/weapon investigations remain unimplemented. No push or remote creation is performed.

## Changes and contracts

`Domain.Api` owns additive generic route modes, route-point receipts/observations and facility launch payload/progress. `Gateway.Api` alone adds and converts the canonical wire fields; `Gateway.Grpc.Api` continues importing those messages and uses existing SubmitOrder/GetStatus/GetView RPCs. `Gateway.Grpc` transport implementation is unchanged; its mock models route sequencing without pretending a queued append executed. `SeaPower.Client` implements guarded native mutation and progress. `SeaPower.Mod` extends only generic bridge argument validation and the opt-in launcher; production runtime/harness source and bootstrap remain separate.

`Waypoint.route_mode = 3` has `LEGACY_IDLE = 0`, `REPLACE_ROUTE = 1`, `APPEND_WAYPOINT = 2`. An omitted mode retains the idle-only legacy behavior. Unknown modes reject. Existing wire field numbers/types and Stage values 0–4 remain; additive Stage values are `ROUTE_MUTATED=5`, `EXECUTION_UNKNOWN=6`, `PREPARING=7`, `AIRCRAFT_SPAWNED=8`, `AIRBORNE=9`. `OrderRequest.facility_launch=6` joins the existing oneof. Results add before/after routes, mode and correlated spawned ID. World observations add inspected planned routes, nullable airborne, loadout eligibility and nullable facility onboard/reserved/cooldown counts. Missing optional values mean unknown, not zero.

At actual dispatch, session/opaque entity, observation freshness, request ID, argument bounds and current eligibility are checked. Native route mutation samples the unit again immediately before editing. Only isolated vessels in Default/PlayerOverride with a proven ordinary reachable navigation graph are supported. Rejection leaves the graph alone. Exceptions after native invocation report execution unknown; the engine is not transactional, and there is no speculative rollback or automatic retry. Duplicate requests return retained status and do not mutate again. After replacement, obsolete pending movement attribution is removed. Append displacement counts toward execution only after the requested waypoint becomes the route head. No verified-arrival status is invented.

The first facility backend supports only a player-owned `airfield_small_1`, `usaf_f-4e`, dynamic valid squadron and `AirToAir`, count one. These are adapter capability limits, not protocol-specific identifiers. Adjacent native validation covers ownership/control, operability, unreserved vehicle/squadron stock, callsign/loadout membership, ammunition, crew/deck, compatible elevator/launchpoint paths and operation conflicts. Native preparation/taxi/takeoff remain in control. Acceptance verifies one pending task and exactly one vehicle/squadron reservation. A bounded native launch ledger subscribes to `Launched`; own spawned objects are immediately normal generic units, including grounded objects. Native airborne observation advances the same request and retains its session-scoped spawned ID. Reset unsubscribes callbacks. No per-airframe hosted fuel/damage/ETA or recovery identity is inferred.

Unreserved aggregate stock, pending reservation, physical onboard count and cooldown-task count are reported separately. Native taxi/runway occupation may delay execution after accepted preparation. Counts do not promise persistent hosted-airframe identities. Snapshots, routes (32), stock/options (12), launch ledger (64), messages and existing receipt queues remain bounded; stock omissions mark truncation.

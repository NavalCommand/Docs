# Task 003 — Sea Power air-facility investigation

2026-10-09. **Live launch and recovery succeeded from a ground airfield, carrier and helicopter ship** on Sea Power **0.8.3-261001**, Unity 6000.0.67f1. Active native facility AI independently requested CAP/AEW sorties while the separate strategic AIPlayer remained disabled. The central distinction is between **request selection**, **native facility decisions**, and **automatic execution**. No production adapter was implemented.

The common backend is not an authority boundary. createLaunchTask does not independently validate faction entitlement, positive count, stock bounds, membership of the supplied squadron/loadout or complete facility health/layout suitability. UI/helper checks and native execution gates are distributed. A future adapter must validate on dispatch and handle a null result; calling the method alone is insufficient.

CoreService uses First lookups, so an absent type/loadout can throw before its descriptive null check. If createLaunchTask returns null, its TaskCompletionSource remains unresolved; even success completes on spawning before takeoff. Do not reuse it as a reliable completed-sortie receipt.

Numbers are reserved at pending-task creation, while AircraftCurrentlyOnBoard decrements at actual takeoff and increments when AddVehicle restores stock. It stayed below the initial value during recovered cooldown, so it is not an exhaustive physical occupancy count. The probe's readyCount label is TotalVehiclesOnBoard, meaning **unreserved stock**, not prepared/combat-ready aircraft. “Available aircraft” must distinguish **unreserved**, **prepared**, **native onboard count**, **launching**, **airborne** and **cooling down**. _vehiclesOnBoard also contains zero-count supported classes; a catalog entry does not mean inventory exists.

Hosted airframes are not continuously instantiated ObjectBase entities. getObjectToLaunch creates the deployed object. DeSpawn destroys it without scoring and creates CoolDownTask keyed by class/squadron/serial; cooldown returns one aggregate count and frees the serial. Campaign tags and crew skill have explicit preservation paths; there is no verified universal persistent fuel/damage/UID continuity. A later launch must be treated as a new deployment unless identity mapping is separately proven.

Recovery is modeled, rather than a generic instant storage operation: plane rollout differs from helicopter/VTOL landing, and elevator/layout conditions determine the sequence. RecoverAll has an explicit instant mode used by campaign code; do not confuse that with ordinary RTB. The cooldown represents turnaround as a timer, not separate observable fueling/arming/repair jobs. A fresh spawned aircraft gets native initialization; detailed condition carryover/repaired damage is unverified.

## Observation safety and experiment limitations

The logger uses RuntimePlugin's bounded queue and plain WriterState; its worker receives strings only. Harmony callbacks and all native reads are on Globals.mainThread (thread 1 in traces). Running cached facility snapshots use JobPerformer.CompleteFixedUpdateJobs with object/collision completion flags; paused snapshots use Update only if those checks pass. This is a managed facility slice, not a global ECS/sensor fence. No live native references travel to workers, and no game-thread disk/network/model work occurs.

The first run intentionally supplies no unsafe fallback when Update never satisfies both job flags. The second moves reads to the validated Task 002 callback. Commands use ordinary main-thread native dispatch and current own authority/operability checks; RTB is withheld during advanced aircraft missile evasion. Formation propagation is not generalized. Error/overflow markers invalidate evidence; short queue states can fall between samples, so absence of a sampled state is not proof it never existed.

The script pauses only an initially unpaused disposable scenario, verifies a wall-second interval, then resumes and requests native 5× compression. This is not production pause ownership. No player/menu was used during the lease. Ready-up timing options remain Realistic, no skip-ready-up flag or forced FixedUpdate is used. Normal flight-deck operations may cap compression further.

Invalid inputs must be rejected before native invocation. Resource shortage can return null; blocked deck/sea state/layout can leave an accepted task waiting; unsafe raw counts can overdraw stock. Occupied-deck, damage, negative/over-count input and unavailable-loadout runtime injections were not performed. Their mechanisms are statically mapped, without invented error codes. Active strategic overwrite, human UI behavior and recovery failures remain separate from successful unit/facility automation.

## Minimal implementation plan within accepted APIs

No AirOperations.Api is proposed.

1. **World.Api:** own friendly facility records, aggregate stock by catalog class/squadron, physical hosted count/capacity, resources, typed facility operation records and availability constraints. Keep unavailable/unknown fields explicit. Deployed aircraft enter ordinary unit observations; do not present them simultaneously as unreserved stock.
2. **Catalog.Api:** content-revisioned facility/type/loadout capabilities, allowed classes/roles, supported recovery/launch types and resource/timing definitions. Keep capability separate from dynamic availability; do not expose proprietary bulk content as part of this investigation.
3. **Orders.Api:** facility-targeted Prepare/Launch, release/hold prepared launch, pending Cancel and possibly Reprioritize after validation. Use the same acceptance/execution/outcome mechanism as generic unit orders, with facility target plus aggregate aircraft/squadron/loadout/count selection. A returned PendingLaunchTask is acceptance; spawn and airborne are separate stages. RTB remains an ordinary deployed-unit order.
4. **Incidents:** retain own request acceptance, preparation-ready, spawned, airborne, recovery begun, stored/despawned and stock-returned where valid native evidence exists. Bind task/subdeployment/session relationships; preserve outcome unknown on loss/unload. Independent consumer cursors and retention gaps remain implementation requirements, not a tested service.
5. **Adapter validation:** resolve selected-side facility/session on dispatch; verify membership/count/callsign/loadout/resource health and current execution restrictions. Map null/exception distinctly from waiting. Do not rely on CoreService's unresolved promise or native backend authority checks.
6. **Controller ownership:** external decider chooses sortie goals/loadouts when responsible; engine executes queue/crew/taxi/takeoff/recovery. Facility AI independently decides sorties on eligible nonplayer facilities. Before external nonplayer ownership, test scoped control of that controller without disabling deck execution or urgent aircraft defense.

Schema questions deferred: per-airframe identity while aggregated, ETA versus remaining work, allied permissions, stable content keys/mod revision, resource categories/units, cancellation after spawning, recovery-failure receipts, lost-supply refunds, count invariants during scene transitions, and exact automatic-controller ownership. External readiness intelligence stays separately sourced from verified facility state; native mission/AI tasking is not automatically external briefing context.

## Architecture delta proposals and risks

ARCHITECTURE.md was not silently changed. Proposed clarifications:

- Add **three native responsibility layers**: disabled NodeCanvas AIPlayer, independently active facility decision routines in AI, and automatic FlightDeck task execution. The Task 002 caveat remains valid for strategic arbitration, but does not mean all native AI is inactive.
- Model **aggregate inventory reservations and asynchronous deployment identity**, rather than persistent hosted ObjectBase airframes. Prepared/physical/available counts are distinct.
- Make **spawn versus takeoff versus recovered storage** explicit order stages; native Launched and CoreService return are insufficient completion evidence.
- State that ordinary pause/resume does not universally complete preparation; the native registered-facility path has specific side effects.
- Keep timed cooldown as the verified turnaround model; defer invented separate repair/refuel controls and general cancellation.

Risk ranking: **P0** external/nonplayer facility ownership and bypassed native validation; **P0** correct asynchronous receipts/stock invariants; **P1** recovery/identity completion and sea-state/damage/layout failures; **P1** safe cache freshness/actual pause intent; **P2** patrol/SAR/strike workflows, allied facility visibility, mod-content invalidation. Unrelated Task 002 track fusion, multiple-consumer service, native gateway/client/UI and scheduler work remains outside this task.

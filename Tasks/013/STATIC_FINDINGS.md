# Task 013 — static findings

**Inspection baseline:** Sea Power 0.8.3 Build 261001 Public Release, Unity 6000.0.67f1. The installed `Seapower-Scripts.dll` SHA-256 is `0FE6AAF2A6D9982E7E2EB41FD6035CB97C149773202C90821D71C00A9FDEB01A`, matching Tasks 001–003 and 012. ILSpy 11.1.0.9782 was used for read only inspection. Decompiled vendor code remains in the local temporary directory; this report records member names and behavior, not source listings.

“Verified” means the installed build’s member/control flow was inspected. “Interpretation” describes the proposed domain mapping. “Unverified” means this task did not exercise the behavior.

## Catalog enumeration

| Native source | Verified behavior | Consequence and limit |
|---|---|---|
| `FileManager.GetSearchDirectories`, `Directories`, `GetFiles` | The active file set includes the game’s `original` and `user` directories plus selected installed content/Workshop directories in load order. File enumeration deduplicates relative paths across active directories. | A modded definition is discoverable by the same path when its directory is enabled. Disabled, uninstalled or unsupported content is outside that catalog. This task did not run with a custom mod enabled. |
| `Utils.openVirtualIniFile`, `IniHandler.CacheVersion` | Virtual INI files merge sections and keys from active directories; the cache version changes when file caches are invalidated. | Reading only the vendor `original` folder misses selected overrides. | `UnitMetadataProvider.OnStart` → `LoadUnitMetadata` → `GetIniNames` | In game mode the provider schedules an asynchronous metadata load. It enumerates `aircraft`, `land_units`, `vessels` and `biologic`, excluding auxiliary names, squadron, variant, shared settings and test files. | `UnitMetadataProvider.CollectUnreferencedAmmunition`, `AmmunitionData` | The provider loads ammunition referenced by units and then scans `ammunition/*.ini` for unreferenced entries, except the special `damage.ini`. | Weapon definitions can be included even when no loaded platform references them. |
| `SensorMetadataProvider.OnStart`, `Sensors` | The provider reads every section of merged `systems/sensors.ini` and creates definitions for `Radar`, `Sonar`, `ECM`, `ESM`, `Visual`, `MAD` and `LaserDesignator` kinds. | Sensor definitions are separately enumerable; they need not be reachable from one unit loadout. Unsupported/malformed definitions may be skipped. |

The runtime count in [Run 1](../../Evidence/Task013/Run1/loader.log) was **642 `UnitData` entries** while the scenario contained two aircraft. The count comprised 558 base keys and 84 generated loadout keys. The provider reported 443 ammunition definitions and 508 sensor definitions for that run’s active content set. Entries by native object type were Aircraft 92, Helicopter 21, Vessel 268, Submarine 70, LandUnit 188 and Biologic 3. This confirms file backed enumeration beyond scenario membership; it does not prove coverage of malformed files or arbitrary plugin generated objects.

`UnitMetadataProvider` creates numeric IDs while loading; the run assigned F-14A 66, Perry 499 and Los Angeles 526. These values are evidence of the current cache, not stable catalog identifiers. File keys are better native names, but overrides can change their contents and the game exposes no persistent content revision hash. Use catalog scoped IDs and a content revision/hash as proposed in Task 012.

## Platform definitions and loadouts

`SimpleObjectParameters` and its subclasses hold type definitions, not deployed units. `UnitMetadataProvider.SchemaTypes` distinguishes vessel, submarine, aircraft, helicopter, land unit, biologic and ammunition parameter shapes. The loader currently discovers the first six platform families through the four directories above; no separate `other` directory was found. The proposal’s platform-description union should explicitly say how a helicopter’s distinct performance fields fit under the air-platform case; it should not fall through to a generic “other” description by accident.

`SimpleObjectParameters._loadouts` is built from `WeaponSystems.AvailableLoadouts` or, for cargo definitions, `Cargo.AvailableLoadouts`. The parser merges loadout-specific system sections with base system sections, resolves station/magazine ammunition, totals repeated ammunition identities into `Loadout.AmmunitionAmounts`, and records `DateBasedAlternatives`, supply accounting, service-entry year and ready-up/cooldown values. It can add `Empty` and `Ferry` when matching sections exist even when they are not named in `AvailableLoadouts`.

`Loadout` is not a complete native equipment object. Its `AmmunitionAmounts` is one part of a fit. Platform `SensorSystemN` sections and sensor definitions are loaded separately into the type’s system data; `_sensorData` describes platform signatures such as visual, radar-cross-section, infrared and acoustic properties, not an installed sensor suite. Catalog presentation can also add pod ammunition and extra stores outside `AmmunitionAmounts`. A complete domain loadout therefore requires resolving base platform capabilities plus loadout overrides, date based ammunition and applicable extra stores.

The parser expands only certain vessel/submarine loadouts into synthetic `UnitData` records. Aircraft alternatives remain in the aircraft type’s loadout dictionary and are also selected as part of FlightDeck launch preparation. Task 003 established that a carrier/airfield holds aircraft stock aggregated by class and squadron; hosted stock is not a set of persistent fitted `UnitInstance` objects. A spawned aircraft becomes an ordinary unit after launch.

These are loadout definitions, not proof that a deployed ship/submarine carries that fit. `Loadout.ServiceEntryYear` and date-based ammunition require an era-aware resolution or truthful alternatives. Do not infer a default if the native definition does not supply one.

## Weapon and sensor capabilities

The native concepts do not line up one to one with the proposed capability types:

- `AmmunitionSimpleParameters`/`AmmunitionParameters` describe munition identity, type, primary/secondary target categories, target-required flag, guidance and midcourse-correction data. `UnitMetadataProvider` also exposes launcher/ammunition compatibility and target-slot limits.
- `WeaponSystem` subclasses describe installed mechanisms such as hardpoints, launchers, guns/CIWS and chaff dispensers. `WeaponEntry` is a player-facing choice for an ammunition group and gathers every compatible system through `ObjectBase.GetWeaponSystemsForAmmunition`. One selectable ammunition may therefore be backed by multiple systems. This supports a capability-oriented `WeaponType`; it does not justify public launcher or hardpoint entities.
- Native `Ammunition.Type` includes projectiles, missiles, torpedoes, bombs, rockets, sonobuoys, `Chaff`, `Noisemaker`, `MOSS`, fuel tanks and other types. This build has no separate `Flare` enum value; a flare capability was not verified.
- Chaff and noisemakers are effect/deployment choices. Their UI entries call `LaunchChaff` or `LaunchNoisemaker` without the ordinary target-selection path. They fit a weapon capability with deployment/effect components and a quantity where the loaded count is defined.
- Active ECM is internally a `SensorSystemECM`, but the player effect menu creates a `WeaponEntry` for it. That entry reports free jam channels, opens an `AttackingWithSystemState`, and routes `EngageWithECM`. The state accepts a map contact or a geographic position; `JamTask` applies sustained jamming or switches/stops a target. A jam channel is capacity, not ammunition. Passive ESM is `SensorSystemESM` and belongs to sensing.
- The native sensor-definition keys live in `SensorMetadataProvider.Sensors`; a platform references these through sensor-system sections. Runtime sensor state is separate (`SensorSystem.IsOn`, `Inoperable`, damage and subtype-specific mode/state). `Vehicle.DetectingSensors` describes sensors that detected a contact, not the contact’s installed sensors.
- Weapon parameters include firing arcs/mount information, while ammunition targeting and guidance restrictions live elsewhere. Geometry and compatible-system details are optional fit components. The exact targeting input should remain a composition of contact/position/bearing requirements, not one `requiresUnitTarget` boolean.

The game has no single generic effect-description field covering all these cases. Damage, jamming, deception and deployment mappings require type-specific interpretation. Exact performance units, sensor-mode coverage and every platform’s full fit were not normalized in this task.

## Actual equipment state

The deployed `ObjectBase` and its `ObjectBaseParameters` have live sensor and weapon system instances. `BaseSystem` exposes operating/inoperable and integrity/damage fields; `SensorSystem` adds sensor operation state; `WeaponSystem` has loaded counts, reload state and subtype-specific status. `ObjectBase.AmmunitionAmountDictionary` is the current UI-facing count by ammunition identity (`getAmmunitionAmountByName`). Weapon systems and magazines also retain their own loaded/reserve counts. `GetAllAvailableAmmo` aggregates magazine contents and loaded weapon counts along type-specific paths. These values must not be summed together without proving the partition, or a single round may be double counted.

Catalog loadout quantities are nominal; the own object’s current ammunition dictionary, sensor switches, inoperability and damage are runtime state. Readiness is not one universal native enum. A domain `Readiness` value needs a documented mapping or should remain unknown when the system-specific state has not been normalized.

## Enemy contact and visibility boundary

The selected taskforce’s `PlottingTable.Vehicles` contains `Vehicle` contact wrappers. A wrapper has observer-side estimate fields (`DetectedPosition`, `ExtrapolatedPosition`, `PositionEstimate`, error ellipse, `Class`, `Side`, `Identified`, `DetectingSensors`) and also retains `Object`/`BaseObject` references to the real object. Other members, including `RealUnityPosition` and `UnityVelocityVector`, can expose truth. A raw wrapper or `BaseObject` is not a safe operational observation.

The inspected map UI gates class text on `Identified`. An identified contact’s “Information” action opens the class encyclopedia. `ObjectInformationViewModel.GetReferenceLoadoutVariant` returns a loadout reference only for player/ally units, so an enemy contact does not select its actual loadout in that page. The separate contact information window uses the plotted vehicle/ECS state and detection information. Task 012 found an engagement-hover path that reads the target’s underlying `BaseObject` for derived calculations; that path is not proof that actual equipment or the exact fit is visible to the player.

## Current NavalCommand adapter context

`SeaPower.Client.NativeGameFacade.CaptureUnits` currently samples only selected-side owned units. `CaptureTracks` reads the player plotting table’s fresh `DetectedPosition`, skips contacts without that field, and exports no type/equipment or uncertainty fields; `UnitSample` and `TrackSample` are separate wire samples today. Those are implementation facts, not constraints on the proposed backend-independent `UnitInstance`. Any future unified representation must retain selected-side filtering and distinguish track identity/authority from own-unit command handles.

## 4. Native automation deep dive

### Advanced aircraft missile evasion: the active default path in this binary

`Globals.useAdvancedEvasion` is initialized to `true`; `Globals._testIsUnitDefenseActive` is initialized to `true`. Runtime settings/assignments can change those defaults. This is distinct from assuming every aircraft will evade.

1. **Threat acquisition.** Native `AI.AIDetection` adds known threatening missiles to the unit's `_dangerousMissiles`; `ESM.createPassiveESMContacts` also adds a missile when it gives an RWR warning to the home unit. `ObjectBase.CheckForThreateningMissile` periodically removes destroyed/nonthreatening missiles and chooses the closest candidate whose connection is not permanently lost. `_missileCheckInterval` defaults to one operational second. The `ThreateningMissile` setter raises incoming alerts for player objects, subject to reported-weapon tracking. Do not expose the missile's hidden launch platform simply because that object is reachable from the warning.

2. **Trigger.** `Aircraft.OnFixedUpdate` calls its state-machine fixed update and then threat checking. `Aircraft.initStates` registers advanced evasion as an any-state transition. Requirements include advanced mode, `ShouldEvadeMissile`, `CanEvadeMissiles`, and either a less urgent current priority or the specific bingo-fuel state. Player aircraft additionally require `OptionsManager.AircraftMissileEvasion`; nonplayer aircraft bypass that player preference. `CanEvadeMissiles` excludes large aircraft and level/dive attack modes. `ShouldEvadeMissile` requires a live missile actually targeting this aircraft, not ignored, positive closing velocity and a time-to-intercept threshold derived from turn capability/relative speed. This is not a generic “all missiles within range” trigger.

3. **Priority and entry.** `AdvancedMissileEvasion` has priority **1**; smaller values are more urgent in the inspected aircraft comparisons. `StateMachine.getTransition` evaluates any-state transitions in registration order before current-state transitions. On entry the evasion switches formation-flight physics if needed, remembers commanded speed, desired altitude and position-override flag, commands maximum configured Mach and lowest preset altitude, limits dive pitch to 45 degrees, optionally launches chaff, updates status text, sets `_lastBaseState`, and picks a strategy. It uses typed state, not just an order string.

4. **Execution/occupancy.** `onFixedUpdate` updates the missile reference and steers away (“cold”) or perpendicular to its velocity. It owns `Motioncontroller.CommandPosition` through `commandPositionOverride`. No constant duration is specified. It finishes on missile disappearance/destruction, target loss, permanent connection loss, or the missile targeting someone else. A slow client cannot infer completion from one elapsed timeout.

5. **Exit/resumption.** Exit restores the remembered numerical speed as a `ConstantSpeed`, desired altitude and previous position-override flag; it resets maximum dive pitch to `float.MaxValue` and records `lastExitTime`. `Aircraft.initStates` transitions finished evasion to `state_default`. **It does not restore `StateMachine.PreviousState` or a saved full order object.** The evasion methods do not remove waypoint tasks; continued native route execution is therefore plausible, but exact engagement/formation/RTB continuation must be exercised. Restoration loses original speed-command type/Mach semantics and does not explicitly restore the prior flight-physics model. Report partial control restoration, not guaranteed universal order resumption.

6. **Concrete collision with a manual order.** In `SeapowerUI.ViewModels.UnitSelectedState.HandleUnit`, the ordinary map-movement branch clears an existing order, can detach formation/patrol membership and, for air units without an active guiding alignment, calls `obj.CeaseFire(report:false, clearOrder:true, formationCheck:true, stopJamming:false)`. Virtual dispatch reaches `Aircraft.CeaseFire`. If advanced evasion is current, it adds the live evaded missile to `_ignoredMissiles` and marks the evasion finished **instead of** taking the normal base cease-fire path. `ShouldEvadeMissile` then refuses that ignored missile until it disappears/is destroyed. Thus this is a verified movement → cancellation → suppressed re-entry path, not just a speculative priority conflict. `InputHandler` also calls `CeaseFire` for a cease-fire action.

7. **Less obvious collision.** A caller bypassing the UI can still change speed/altitude or insert tasks. Advanced evasion's exit can overwrite a speed or altitude changed during evasion with the values remembered at entry. Entry points have no universal “protected native action” check. Refusing commands only when they directly set a new state would be insufficient.

**Proposed V1 protection (inferred design, not implemented):** On the game thread, reject route replacement, speed/altitude changes, cease-fire/order cancellation, engagement/formation changes and refuel/RTB requests while advanced evasion is active unless a later, specifically verified exception is allowed. Check all affected formation units, not only the leader. Expose a typed busy reason and state-change time, without exposing hidden missile identity/position. Recheck immediately before execution; do not replay a rejected command automatically after evasion using stale context. The exact safe allowlist remains experimental.

### Other discovered urgent paths and selective control

`Aircraft.initStates` also registers `AircraftStates.EvadeMissile` at priority 2 when advanced mode is false. Its trigger uses `_missileToEvade`; `Missile.TerminalApproach.ApproachTarget` assigns that field on a close approach. `EvadeMissile` commands a break/chaff and max Mach, finishes after more than two operational seconds or threat disappearance, then clears that missile field and restores speed/position override. **`AircraftStates.MissileEvasion` also exists but was only constructed in the inspected initialization; the active transition registrations point to `EvadeMissile` and `AdvancedMissileEvasion`.** Do not attach to a plausible class name without checking registration.

`SubmarineStates.TorpedoEvasion.onEnter/onFixedUpdate` uses `ThreatingTorpedo`, sets status, launches noisemakers on an interval, changes preset depth/telegraph and chooses deep-dive vs turn/layer tactics. `VesselStates.TorpedoEvasion` and `CounterLaunch` also exist. Their complete entry/exit/manual-interference paths were not traced to the same depth; protection of surface/submarine urgent states is a follow-up before those unit families receive commands.

Selective controller shutdown is **unverified**. Inspected switches are broad and inconsistent: `OptionsManager.AircraftMissileEvasion` is player-specific; `Globals.useAdvancedEvasion` selects evasion implementation; `Globals._testIsUnitDefenseActive` is global; `Aircraft.AllowAI()` returns `DM_TestTools._aircraftAIWorksForPlayer`, while `CanUseAIStates` uses another player/experimental distinction. None establishes a clean per-unit, per-subsystem handover preserving all other automation. Do not disable behavior trees or set `HasControl=false` as a substitute for command authority.

## 5. Perspective and security boundary

### Player versus AI

`Taskforce` constructs a plotting table regardless of side, but only the player side installs `AddVehcleListeners` for player reporting/UI alerts. AI identification states query `GetMapVehicle(_taskforce)`; `AI.AIDetection` selects taskforce or unit-local plotting data for certain submerged conditions. These establish a nonplayer observation path. They do not establish that player UI lists, global IDs or all AI decisions are suitable for a selected AI faction.

Use a selected **taskforce instance**, not global `_playerTaskforce`, to obtain contacts. `ObjectBase.GetMapContactID`/`Id` use the player's table and cannot serve as a faction-neutral identity API. Determine alliance sharing from actual selected-side table provenance; exact shared-sensor and communications limitations remain unverified. A taskforce-wide observer is an aggregate command perspective, not necessarily what every individual submerged unit can currently receive.

### Minimal filtration proposal

Own-state collection may read the selected taskforce's actual objects in V1, subject to an explicit own/friendly access policy. Contact collection must start from its plotting table and whitelist observer-produced values:

- Position from nullable `Vehicle.PositionEstimate`, including its uncertainty (`PositionEigpairs`); distinguish fresh detection and extrapolation. A stale reactive `Position.Value` alone is insufficient.
- Sourced classification/side/altitude, detecting sensor categories and track age. Unknown stays unknown; no fallbacks to true unit class, nation, height or name.
- Adapter-assigned opaque IDs scoped to observer and session. Internal `ObjectBase` correlation can support V1, without exporting UID/entity handles or promising one track per physical unit in the domain contract.
- Contact disappearance recorded as loss/deletion according to visible provenance. Do not turn an authoritative destruction into a confirmed enemy loss without evidence available to that observer.

Concrete leak paths requiring exclusion:

| Reachable path | Hazard |
|---|---|
| `ObjectsManager` global lists / UID lookup | Enumerating objects reveals undetected units. |
| `Vehicle.BaseObject`, `RealUnityPosition` | True identity, damage and location remain reachable inside a contact. |
| `Vehicle.UnityVelocityVector` | `UpdateFromECS` copies true `Object.UnityVelocityVector`, optionally perturbed by TMA; membership in a contact table does not make this measured velocity. |
| `Vehicle.CurrentRelationship`, `GetMapType`, map/render helpers | Helpers can inspect true object type, destruction or taskforce; do not treat every UI convenience as a perception-safe field. |
| `CoreService.VehiclesInArea` / `WatchArea` DTOs | Include `BaseObject.name`, `UniqueID`, true destruction and packed entity. Also dereference a nullable position estimate without comprehensive guard in the inspected enumeration. |
| `CoreService.GetUnitsInTaskforce`, `GetObjectInfo`, `GetUnitPosition` | Raw UID-based access with no observer authorization in those bodies. |
| Engagement/Pk prediction and incoming-weapon registry | Can use exact opponent motion, target intent, durability and launch source. `GameMain.rebuildIncomingWeapons` builds a truth-based registry; this is not a sensor incident stream. |
| Editor/scenario reconnaissance, reveal overrides, briefings and triggers | Author-supplied truth and player intel can contaminate sensor tracks. `SensorSystemsLink._unitsToRevealOverride` is an explicit lead to audit. |

Field provenance, authority to command and instantaneous ability to accept a command are separate checks. Native RPC is evidence of integration possibilities, not a security boundary to relay wholesale.

### Lifecycle and player/AI differences

`CurrentOrder` describes only part of active work. There are also queued visual tasks, `_currentEngageTasks`, alignment tasks, formation/patrol/deck states and the state machine. `UserRootNode.AddTaskNow` inserts at the front and handles immediate insertion during child execution. `GoToWaypointTask` distinguishes reaching and stopping, but its `RemovedOrFinished` callback does not itself expose a reason. Its successful finish can include time-follow or an aircraft overshoot failsafe. Build receipts from actual callbacks/reasons rather than inventing a universal native success event.

`Order.setOrder` refuses noncontrollable units. `AcceptsOrdersFromPlayer` mainly suppresses display text inside this method, whereas UI entry checks determine player access. The target-object `ObjectBase.setOrder` overload refuses grounded aircraft/helicopters; the geographic overload does not have that same guard. The inspected `CoreService.GoToWaypoint` and altitude setter use UID lookup directly. Therefore externally mutating an AI object is plausible, but native AI may still reassign activity. Native `AI` itself calls `setOrder` for identification/RTB and uses engagement/waypoint tasks for other work. AI ownership arbitration remains an experiment, not a completed capability.

## 7. Runtime, concurrency, timing and IPC

### Initialization and lifetime

`GameMain.Start` invokes `GameInitializer.init` in standalone mode; update paths require `_initialized && !_closing`. `MissionManager.DoLoad` schedules initialization; `DoUnload` releases terrain/resources, calls `JobPerformer.CleanUp`, unloads the mission scene, then calls `GameTime.StopTimeCompression`. `GameMain.OnDestroy` handles teardown. Destroyed/swapped objects, taskforce transfer, scenario restart, save-load reconstruction and ECS entity lifetime mean an adapter must invalidate handles/subscriptions and queued commands on a new session. `ObjectBase.swapObject` and `TransferToTaskforce` are additional invalidation/authority-change points. Pause alone does not imply reference invalidation, but does not prevent UI mutations.

### Candidate safe points, not established hooks

`GameMain.PerformFixedUpdate` performs:

1. `JobPerformer.CompleteFixedUpdateJobs` (wave sampling, object calculations, collision avoidance).
2. `GameFixedUpdater.fixedUpdate` (including time, sensors and taskforces).
3. Per-object `OnFixedUpdate`.
4. `JobPerformer.StartFixedUpdateJobs`.

A mailbox drain/snapshot **immediately before step 4** is a promising hook for fixed-update-owned state; a postfix on `PerformFixedUpdate` is too late to assume jobs are quiescent. This remains inferred: inspect all touched data and sensor/plotting ECS dependencies first. `TaskforceManager.OnUpdate` schedules geographical synchronization and updates `PlottingTableSystemGroup`; contact tables also update incrementally. A callback on `PlottingTable.Updated` is useful for incident capture, but not proof that all own objects/environment values share an atomic epoch. `GameMain.LateUpdate` also does not explicitly complete all jobs. Do not claim any one of these is a certified coherent snapshot point yet.

Copy only bounded plain immutable data on the main thread after relevant jobs are complete. Background IPC workers must never touch `ObjectBase`, transforms, `ReactiveProperty`, ECS managers/buffers, or live collections. Use bounded queues and re-resolve authority/state on dispatch. Preserve observation sample time/age rather than presenting asynchronous sensor estimates as measurements at the current snapshot time.

Global `RPCServer.Start` captures `SynchronizationContext.Current`; `RPCServerUtils.SetupServer` sets that context and a `JoinableTaskFactory` on `JsonRpc`, with cancellation on closed connections. This is concrete native marshaling evidence. It does not certify all async code or guarantee a public listener. `RPCServer`'s inspected `Update` is empty; its `WebSocketServer` field alone proves no listening port. `ScriptRuntime.LoadFromIni` creates `CoreService`, loads script modules and drives a Vuplex/WebView runtime. Native scripting is a candidate integration route to evaluate before adding another loader, not a working external API confirmed in this investigation.

No third-party assembly-loader/hooking framework was present in the inspected top-level installation layout. An isolated managed loader with targeted interception is a plausible alternative, but none was selected, installed into the game or compatibility-tested. Loading, managed profile, dependencies and patch ordering must be established before treating proposed hooks as deployable.

### Operational clocks and pause

`GameTime.OnUpdateUnpaused` advances `missionElapsedTime` and `missionSessionTime` by `TimeCompression * Time.deltaTime / Time.timeScale`. `GameTime.OnFixedUpdate` separately advances `simulationTime` and `simulationTick`. Unity time scale is capped at `_physicsTimeScaleCap=10`, while game compression can be higher; fixed delta and sensor delta are adjusted. `SetAdaptiveFixedDeltaTime` switches Unity's fixed step according to FPS. Thus a tick is not a universal duration, and frame mission time is not interchangeable with physics time. `Environment.DateTime` supplies scenario calendar time; its display/local-time basis requires confirmation before choosing an absolute operational timestamp.

`Pause` can force a fixed update if no fixed update has occurred, then sets compression zero and UI pause state, with optional audio muting. `UnPause` restores the native selected compression index. `TimeCompression` setter also updates environment and completes pending controlled flight-deck launch preparations when positive. `StopTimeCompression` means **1× execution**, not pause. Use the native pause functions with their side effects, not raw `Time.timeScale`, but do not assume they preserve an external arbitrary multiplier exactly.

There is no inspected native pause owner token. A proposed privileged adapter should record whether it acquired an unpaused run, track user/menu/time-control changes during its lease, and release only its own still-valid pause. Merely checking `IsPaused` at resume cannot distinguish a new player pause while already scheduler-paused. Observe pause intent/control paths, not only value changes. `TimeCompression` setters, UI/menu calls and mission unload all require coverage; reset any lease on session change.

Paused `GameMain.Update`/`LateUpdate` remain eligible; taskforce contact `OnUpdate` explicitly returns on pause. Normal physics-driven execution stops, but the UI can mutate orders and data while paused. Native code stores pending launch preparations until resumed. Consequently paused command acceptance is plausible, but mailbox dispatch and coherent paused snapshots require a main-thread path that runs without FixedUpdate. Do not force fixed updates to execute paused decisions: that can advance `simulationTime`/tick. Verify after-pause job completion and command execution in a dedicated experiment.

The inspected `GameTime.LoadStateFromFile` reads `MissionElapsedTime` four times without assigning saved clocks; `SceneCreator` calls it for load. This is a concrete reason to test save/load timestamp behavior and introduce adapter session epochs. It is not proof that other load paths cannot restore time.

| Slow-decider mode | Assessment |
|---|---|
| Synchronous | Likely after pause ownership/paused mailbox validation. Trigger at first observed mission-time deadline crossing, settle/copy state, pause, accept decision on main thread, conditionally release lease. Report approximate crossing. |
| Hybrid | Likely with same safeguards; computation runs outside the game. One in-flight evaluation and explicit staleness handling are practical initial constraints. Missed-cycle policy remains undecided. |
| Fully asynchronous | Likely and easiest to isolate from runtime control. Bound work and validate stale commands/current automation on application; never block the game on a slow decider. |
| Exact boundary | Unverified. Variable frame/fixed steps and compression permit overshoot. No inspected deadline-stop member supports an exact operational-time guarantee. |

### Local IPC options, still open

Windows named pipes, loopback TCP, or a WebSocket/JSON-RPC route are plausible between thin C# and C++. Native StreamJsonRpc/WebView plumbing is a useful compatibility lead; a public external socket was not verified. Pipes need framing/access control and Mono support validation; TCP needs explicit local binding/framing/session checks; WebSocket adds framing/library integration but may align with native tooling. A file polling bridge introduces I/O/latency and is not established as necessary. Shared memory adds synchronization complexity and is not needed for the first proof. These are options, not adopted architecture or installed dependencies. Keep all blocking I/O off Unity's main thread and isolate dependencies from Unity's bundled versions.

## 8. Environment, incidents and briefing

Terrain queries have real modeling uses: `TerrainUtils.GetRealHeightInMetersAt` returns signed height, wrapping `GetHeightAt`; map depth/corridor checks can distinguish land/water. `GetHeightAt` uses a lock and loaded terrain/DEM paths. Disabled terrain and invalid latitude paths can return `-10000`; that value must not be reported unconditionally as actual bathymetry. Coverage/resolution/cost were not measured. Use bounded point/corridor queries and verify their validity/sentinel conventions before exposing them.

`Environment.getOceanNoise` combines environment-map value, ambient parameters, sea state and floe ice. `getLayerHeight` caches a generated per-tile negative layer height for sufficiently deep water, otherwise uses a positive sentinel; it seeds `UnityEngine.Random`. `getXLayerAttenuation` also seeds that global RNG. Calling these “readers” can change simulation state/RNG, so cache existing modeled results or establish an isolation strategy before adding new queries. `SubmarineStates.TorpedoEvasion` actually uses layer height for evasion, establishing a tactical rather than purely cosmetic role. Detailed sound-speed profiles, acoustic ray queries, forecast data and a universal obstacle database were not verified. Cloud/wind representation exists in the broader environment system, but a complete gameplay-versus-render-only audit was not performed.

Suitable incident leads are typed state transitions, selected-table new/deleted/dormant contacts, waypoint reached/interrupted/removed callbacks, own-system inoperability/damage changes and own missile warnings. `StateMachine.OnStateChanged` fires when `CurrentState` is assigned, before `StateChangeTime` is set and before `onEnter`; record transition intent minimally and finalize snapshot later. Player alert/voice pathways are rate-limited/player-specific and cannot be the only AI observer incident source. Damage/system changes can use own-unit reactive/property subscriptions, with lifetimes tied to session/object validity.

Do not replay global `DM`/`EventLog` or `GameMain.rebuildIncomingWeapons` as faction incidents. Each record needs a visibility decision at capture time; a later contact appearance must not retroactively reveal an earlier hidden launch. A snapshot might miss the two-second fallback aircraft evasion completely. Proposed adapter retention therefore uses bounded records, per-consumer cursors/acknowledgments and explicit retention gaps; no single destructive queue shared by GUI, recorder and commander. These are required semantics, not an implemented incident taxonomy.

`MissionBriefViewModel` loads localized XML panes/assets from mission INI settings; `GameInitializer.init` creates the player briefing screen. Native objectives, triggers and scripted tasks also exist. The inspected paths establish player presentation, not authored per-AI briefing availability. Continue externally supplied tasking/briefing/intelligence with provenance; do not treat scenario fields, scores or objective truth as sensor observations.

## 9. Proposed thin C# adapter outline (no implementation)

1. **Lifecycle binding:** Load through a validated integration mechanism; attach only once mission initialization finishes. Resolve selected taskforce and reset a session epoch on unload/restart/load. Validate assembly hash/member availability and detach subscriptions on teardown.
2. **Observation collector:** Own-unit whitelist over selected membership; contact whitelist over selected plotting table. Resolve estimates, source/age/uncertainty, convert native units, map internal references to opaque observer IDs. Read initialized catalog caches separately. Measure bounded cost.
3. **Game-thread mailbox:** Receive plain requests from a worker; re-resolve object/session/authority, validate native applicability and current busy state, and call verified native functions. Separate acceptance from start, completion, interruption and failure. No synchronous remote wait inside callbacks.
4. **Automation guard:** Recognize current typed evasion state and relevant formation members immediately before mutation. Keep native behavior active. Reject unsafe slow commands while protected; record rejection locally for consumers. Broaden only after unit-family traces.
5. **Incident capture:** Subscribe/intercept only validated observation/own-unit paths, copy minimal records and retain independently of snapshots. Ensure callbacks do not dereference disposed game state later on workers.
6. **Privileged runtime control:** Main-thread pause request and adapter pause lease independent of operational observations. Cover manual/menu intent and teardown; do not expose pause/compression in naval-world facts.
7. **IPC worker:** Serialize immutable snapshots/records, receive bounded requests, manage reconnect/session rejection/backpressure and shutdown. Native scripting/RPC versus a separate loader/pipe remains a discovery decision; C++ transport/domain work is deferred.

This outline assigns responsibilities and evidence-backed native entry candidates; it does not choose a wire schema, framework, repository graph or client architecture.

## 10. Recommended V1 vertical slice after review

Use one isolated mission with one controllable own aircraft, one initially undetected opponent, and a reproducible incoming-missile situation. Start with the player taskforce to limit unresolved command arbitration, while testing AI-side read access separately.

Acceptance sequence:

1. Establish session/side and list own position, native route/task state, speed and a small equipment subset.
2. Confirm the hidden opponent is absent. After detection, expose one opaque track with estimate/source/uncertainty and no raw identity/velocity/UID. Confirm loss/extrapolation behavior.
3. Add one ordinary native waypoint at a safe nonbusy moment, observing acceptance, execution and reached/removal outcomes. Avoid engagement and full route replacement initially.
4. Observe advanced missile-evasion entry and a retained incident; reject a movement/cancel request while busy and verify native maneuver continues.
5. Observe exit and assess route continuation/restored controls without assuming it. Confirm short incidents remain readable independently by two consumers.
6. Acquire/release an adapter pause while unpaused; repeat with a player's pre-existing pause and a player pause intent during an adapter lease. Neither must be inadvertently released. Reload and prove old commands/IDs are invalidated.

This is a recommended demonstrator, not one executed here. Add AI-side writing only after proving a bounded authority mechanism preserves defensive automation.
